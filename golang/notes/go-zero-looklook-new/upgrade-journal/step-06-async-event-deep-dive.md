## 2. 调用链全景（api → rpc → handler → logic → model）

以 `POST /order/v1/homestayOrder/createHomestayOrder` 为例：

```
Client (curl + JWT)
    │ HTTP POST
    ▼
Layer 1: order-api :1001
    ├─ routes.go              (goctl 生成)  [挂路由 + rest.WithJwt]
    ├─ createHomestayOrderHandler.go      (goctl 生成)  [Parse JSON]
    ├─ api-side logic/facade              (手写)        [TravelRpc.HomestayDetail 跨服务校验]
    │      ↓
    │   gRPC over HTTP/2 (TCP socket)
    │      ↓
    └─ (进 RPC 进程)
    │
Layer 2a: travel-rpc :2003                (被 api-side 跨服务调用)
    └─ travel-rpc 内部: travel.HomestayDetail → MySQL 查 homestay
    │
    │
Layer 2b: order-rpc :2001
    ├─ order.go (main)                    (启动 zrpc server, RegisterOrderServer)
    ├─ server/orderServer.go              (goctl 生成)  [调 logic]
    ├─ rpc-side logic/createHomestayOrderLogic.go  (手写)  [真业务]
    │      ├─ TravelRpc.HomestayDetail  ← 又调一次 (冗余!)
    │      ├─ 计算 liveDays + 价格
    │      ├─ HomestayOrderModel.Insert  ← MySQL INSERT
    │      └─ AsynqClient.Enqueue  ← Redis ZADD (defer 任务)
    │
Layer 3: docker 中间件
    ├─ MySQL looklook_order.homestay_order   (新行)
    ├─ Redis asynq:{default}:scheduled       (ZADD 新 task)
    └─ (30 分钟后) mqueue-job.CloseHomestayOrderHandler fire
       → 改 trade_state = -1
```

### 关键代码片段

**api 侧 facade（"门面层"）**：
```go
// app/order/cmd/api/internal/logic/homestayOrder/createHomestayOrderLogic.go
homestayResp, err := l.svcCtx.TravelRpc.HomestayDetail(l.ctx, ...)  // 跨服务 #1
resp, err := l.svcCtx.OrderRpc.CreateHomestayOrder(l.ctx, &order.CreateHomestayOrderReq{
    UserId: ctxdata.GetUidFromCtx(l.ctx),                            // ← JWT ctx 出来
    ...
})
```

**rpc 侧 logic（"真正的业务层"）**：
```go
// app/order/cmd/rpc/internal/logic/createHomestayOrderLogic.go
const CloseOrderTimeMinutes = 30   // 生产值 (我们实验时改过 1)

// 写到 MySQL
l.svcCtx.HomestayOrderModel.Insert(l.ctx, nil, order)

// 写到 Redis (asynq defer 任务)
l.svcCtx.AsynqClient.Enqueue(
    asynq.NewTask(jobtype.DeferCloseHomestayOrder, payload),
    asynq.ProcessIn(CloseOrderTimeMinutes*time.Minute),
)
```

### 教学要点

| 概念 | 解释 |
|------|------|
| **api 侧 logic vs rpc 侧 logic** | 同名不同文件。同一个 `createHomestayOrderLogic.go`，一个在 `cmd/api/internal/logic/`（facade），一个在 `cmd/rpc/internal/logic/`（真业务）。**两边各自有自己的 `svc.ServiceContext`**。 |
| **goctl 生成代码定位** | 看 `// Code generated by goctl. DO NOT EDIT.` 注释 — 这些改动不能手改，要改 `.api` 文件再 `goctl generate`。 |
| **JWT 跨进程不会自动传** | `api-side` 用 `ctxdata.GetUidFromCtx(l.ctx)` 拿 userId 后，必须**手动塞进 gRPC req**（`UserId: userId`）。否则 order-rpc 拿不到。 |
| **同服务 2 次跨 RPC** | api-side 和 rpc-side 都调 travel-rpc.HomestayDetail。这是**冗余 (N+1)**，但好处是 rpc 端可以独立验证、可单测。 |
| **svc.ServiceContext** | 是 go-zero 的依赖注入 container。所有依赖（zrpc client、sqlx model、asynq client）都从这里取。 |

## 3. 异步事件家族 — 4 类任务

**核心认识**：go-zero 用了两种异步框架：
- **kq (Kafka wrapper)**：跨服务 pub/sub（生产者消费者可解耦）
- **asynq (Redis-based)**：本地应用的延迟 + 定时 + 即时

### 事件 A — kq (Kafka) pub/sub

| 项 | 内容 |
|----|------|
| **业务** | 支付完成后通知 order-mq 更新订单状态 |
| **生产端** | `app/payment/cmd/rpc/internal/logic/updateTradeStateLogic.go:92`  `KqueuePaymentUpdatePayStatusClient.Push(json)` |
| **消费端** | `app/order/cmd/mq/internal/mqs/kq/paymentUpdateStatus.go:Consume()` |
| **Topic** | `payment-update-paystatus-topic` |
| **中间件** | Kafka 容器 (host 端 `127.0.0.1:9094`) |
| **Docker 验** | `docker exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9094 --topic payment-update-paystatus-topic` |

### 事件 B — asynq Schedule (cron)

| 项 | 内容 |
|----|------|
| **业务** | 每分钟"结算给商家" demo (源码是空 demo, 实际留待业务实现) |
| **注册方** | `app/mqueue/cmd/scheduler/internal/logic/settleRecordJob.go:15`  `Scheduler.Register("*/1 * * * *", task)` |

## 4. 关键发现 — asynq 在这个版本的 `{queue}` 命名空间

### 真相

我们的 asynq 用的版本（hibiken/asynq + go-zero 集成）写 Redis 时 **用 `{<queue>}` 大括号包起 queue name**，所以实际 key 名是：

| 我开始以为的 | 实际是 |
|--------------|--------|
| `asynq:scheduled` | **`asynq:{default}:scheduled`** |
| `asynq:deferred` | **不存在**（新版本不用这个 key）|
| `asynq:task:<id>` | **`asynq:{default}:t:<id>`** （`:t:` 不是 `:task:`）|
| `asynq:queues:default` | **`asynq:{default}:scheduled`** 队列直接体现在 key 里 |
| `asynq:retry` | **`asynq:{default}:retry`**（同样 namespace）|

我们当时的"实验 1"一开始一直 ZRANGE `asynq:deferred` / `asynq:scheduled` 都查不到，**不是 task 没进去，是 key 名错了**。

### 怎么验的

```bash
# 1. 下单
TOKEN=...
START=...; END=...
curl -X POST :1001/order/v1/.../createHomestayOrder ... | jq -r .data.orderSn

# 2. 加 DEBUG log 看 Enqueue 返回的 taskInfo (含 State:scheduled 字段)
#    (debug log 改完已 commit 清掉)

# 3. ★ 正确的查法
REDIS='docker exec redis redis-cli -a G62m50oigInC30sf'

$REDIS KEYS 'asynq:*'                  # 列所有，看到 asynq:{default}:scheduled

$REDIS ZRANGE 'asynq:{default}:scheduled' 0 -1 WITHSCORES
# 输出: <task-id>
#       <unix-float-timestamp>

$REDIS HGETALL 'asynq:{default}:t:<task-id>'
# 输出: state=scheduled, type=defer:homestay_order:close, payload={"Sn":"..."}
```

### 经验教训

1. **永远先 KEYS '*' 列一下**，再决定查哪个 key
2. **现代 asynq 不用 `asynq:deferred`** — 这是老版本遗留的笔记（Google 出来的多是老版本）
3. **`{<queue>}` 大括号是 asynq 的"queue 命名空间"** — 多队列时清晰隔离

## 5. 关键发现 — closeOrder.go 是"沉默成功"

`app/mqueue/cmd/job/internal/logic/closeOrder.go` 的代码结构：

```go
func (l *CloseHomestayOrderHandler) ProcessTask(ctx, t) error {
    // 1. 反序列化
    json.Unmarshal(t.Payload(), &p)
    if err != nil {
        return errors.Wrapf(ErrCloseOrderFal, "payload err:%v", err)
    }
    
    // 2. 查 order
    resp, err := OrderRpc.HomestayOrderDetail(ctx, ...)
    if err != nil {
        return errors.Wrapf(ErrCloseOrderFal, "get order fail ...")
    }
    
    // 3. 如果还是"待支付" → 改 -1
    if resp.HomestayOrder.TradeState == model.HomestayOrderTradeStateWaitPay {
        OrderRpc.UpdateHomestayOrderTradeState(ctx, ...)
    }
    
    return nil   // ← 成功路径无任何 log
}
```

### 加上 yaml 配置 `Log.Level: error`

```yaml
# app/mqueue/cmd/job/etc/mqueue.yaml
Log:
  ServiceName: mqueue-job
  Level: error   ← 只打印 error/fatal
```

**结果**：closeOrder 跑了 + 改了 trade_state = -1，但 **mqueue-job.log 里完全没有"closeOrder 跑过"的痕迹**！

### 实验 3 怎么验的

我们当时设 `CloseOrderTimeMinutes = 1`，新建订单：
- 1 分钟不到，MySQL `homestay_order.trade_state` 从 0 改成 -1 ✓
- `tmp/logs/mqueue-job.log` **没有任何新行**（无 log 是符合预期）

验成功的 3 个间接证据：
1. MySQL `trade_state = -1` ✓
2. `asynq:{default}:scheduled` ZSET 里那个 task 消失 ✓
3. `asynq:{default}:processed:2026-08-06` SCARD > 0 ✓

### 反思

1. **"沉默成功"是常见的踩坑模式** — 只看 log 验不出东西
2. **验证系统行为应该用副作用而不是 log**：写库、改状态、发外部请求 — 这些是 ground truth
3. **生产代码可考虑加一行 `logx.Infof("[closeOrder] cancel sn:%s", p.Sn)`** — 但要权衡日志量

## 6. 修正的 Bug — Kafka Brokers 端口

### Bug 描述

```yaml
# app/order/cmd/mq/etc/order.yaml
PaymentUpdateStatusConf:
  Brokers:
    - kafka:9092      # ← 这是 docker 服务名 + 内部端口
```

```yaml
# app/payment/cmd/rpc/etc/payment.yaml
KqPaymentUpdatePayStatusConf:
  Brokers:
    - kafka:9092      # ← 同问题
```

我们在 host 模式下跑，**`kafka:9092` 在 host 上解析不到**。这是历史包袱（教程作者默认跑在 docker network 内）。

### 修复

`docker-compose-env.yml` 里 `KAFKA_ADVERTISED_LISTENERS`：
```
PLAINTEXT://localhost:9094           ← host
PLAINTEXT_CONTAINER://kafka:9092      ← 容器内
```

对应端口映射：
```
'9092:9092'   ← host:container，内部用
'9094:9094'   ← host:container，外部用
```

→ host 必须连 `127.0.0.1:9094`。

```diff
-    - kafka:9092
+    - 127.0.0.1:9094
```

### 修复效果

- v3.12 commit 后，order-mq.log 不再是 0 字节
- 应该能看到 kafka client connect success 消息
- payment-rpc.Push 也能真落到 Kafka

### 教训

> **所有 host 模式跑的服务，跨 docker 的连接都必须用 `127.0.0.1:<映射端口>` 不用 docker 服务名**
>
> 这是 Step 1 已经踩过 (mysql/redis) 的坑，我们 2026-08-05 阶段过了；2026-08-06 又踩了 kq 版本。

## 7. 调试方法论沉淀

### 7.1 "沉默失败" 调试模板

```
现象: 做某个动作 → 副作用看起来没发生
步骤:
  1. 加 DEBUG log 看是否到达这个代码行 (用 logx.Errorf 保证 yaml level=error 也能看到)
  2. 看到代码行到达 → 查返回值
  3. 没看到 → 上游早 return 了
```

### 7.2 "key 不存在" 调试模板

```
现象: KEYS 列表没有我以为的 key
步骤:
  1. 列 KEYS 'pattern*' (涵盖常见前缀)
  2. 看最近的 version 文档/源码 — key 命名可能改了
  3. 找历史项目示例代码 (而不是博客) — 博客可能过时
  4. 用 DEBUG log 暴露实际写入的 key (如 taskInfo 中的 ID 反推)
```

### 7.3 "调通了但 log 没出来" 调试模板

```
现象: 业务副作用有，但 log 看不到
步骤:
  1. 检查 yaml 配置 Log.Level 是 error 还是 info
  2. 检查代码里用的是 logx (尊重 level) 还是 fmt/asynq 自带 logger (不尊重 level)
  3. 把"行为发生"用其他副作用验证 (DB/Redis/外部调用)
```

## 9. 反思 (本轮)

### 9.1 我踩过的 3 个真错

| # | 错的事 | 真实应该 | 教训 |
|---|--------|----------|------|
| 1 | 给用户 `asynq:scheduled` / `asynq:task:<id>` (扁平) | `asynq:{default}:scheduled` / `asynq:{default}:t:<id>` | KEYS 一下再确认；不靠旧文档 |
| 2 | 用 shell alias `$REDIS=...` 没考虑 zsh 不做 word splitting | 用 `bash` 子 shell 或每条命令字面写完 | zsh/zsh 的隐藏差异要主动避开 |
| 3 | 给的 redis 命令忘记 `-a G62m50oigInC30sf` 密码 | 任何 redis 命令都带 `-a` 或 `REDISCLI_AUTH` env | redis 6+ 必须认证，提前规划 |

### 9.2 用户给的关键 facilitation

- 用户主动发现 "order-mq 未起" 其实是 step-02.5 的误判 (没 log = 看不到 ≠ 没运行)
- 用户帮我定位 "log 没输出" 的根本原因 (closeOrder 是沉默成功 + yaml level=error)
- 用户主动指出 shell alias 在 zsh 不工作

### 9.3 学到的 go-zero 微服务设计模式

1. **api 侧 + rpc 侧分离**：api 侧做鉴权 / facade；rpc 侧做真业务
2. **同服务 2 次跨调用**：rpc 端可独立验证 (defensive)
3. **JWT 跨进程不自动传**：必须手动塞 req
4. **svc.ServiceContext 是依赖注入容器**：所有 zrpc/sqlx/asynq client 都从这里取
5. **asynq 不止 cron**：也支持 defer 和即时 queue，是个轻量任务分发器
